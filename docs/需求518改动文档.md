# 需求 518 改动文档

## 1. 需求范围

本次只处理 `需求518.md` 中明确提出的内容，不修改无关业务逻辑，不调整原有小程序接口字段。

改动点：

1. 小程序抢单商品按商品列表轮询，不再固定抢第一个商品。
2. 当天订单完成数达到任务数量后禁止继续抢单；完成数量按第二天自然重新统计，不做立即清零。
3. `/miniapp/ctrl/do_withdraw` 新增提现地址参数，后台提现记录展示该地址。
4. 后台充值和提现增加审核流程；超管操作不需要审核。
5. `/miniapp/user/do_register` 新增提现密码参数，用于设置用户提现密码。

新增小程序接口字段仅两个：

- `withdraw_address`：提现地址。
- `cash_password`：提现密码。

## 3. 抢单商品轮询方案

当前逻辑问题：

- `RotOrder.php` 中商品查询按 `sort desc,id asc` 取第一条有效商品。
- 多次抢单时商品不会变化，不符合“轮着商品抢”的需求。

修改方案：

1. 查询当前语言下全部有效商品。
2. 如果当前语言无商品，则回退中文商品。
3. 根据当前用户当天第几单计算商品下标。
4. 预览订单和提交订单使用同一个商品选择方法。

核心规则：

```php
$goodsIndex = ($todayDan - 1) % count($goodsList);
$goods = $goodsList[$goodsIndex];
```

示例：

商品列表为 `[A, B, C]`：

- 第 1 单：A
- 第 2 单：B
- 第 3 单：C
- 第 4 单：A
- 第 5 单：B

## 4. 每日任务完成数方案

当前问题：

- `submit_order()` 里提交订单后直接把 `task_update_status` 设置为 `0`。
- 实际效果会变成“抢一单后就不能继续抢”，不符合“完成当天任务后不能再抢”。

修改方案：

1. 每日完成数继续按 `complete_time >= 当天开始时间` 且 `status = 2` 统计。
2. `orderInfo()` 和 `submit_order()` 在抢单前校验：

```php
if ($completedCount >= $orderNum) {
    // 禁止继续抢单
}
```

3. `submit_order()` 不再每次提交就关闭 `task_update_status`。
4. `Order::do_order()` 完成订单后重新统计当天完成数：

```php
if ($completedAfter >= $orderNum) {
    // 关闭当天继续抢单
}
```

5. 第二天无需手动清零，因统计基于当天 `complete_time`，自然重新计算为 0。

## 5. 提现接口新增提现地址

接口：

```text
POST /miniapp/ctrl/do_withdraw
```

新增参数：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| withdraw_address | string | 是 | 提现地址 |

原有参数不变：

- `num`
- `type`
- `paypassword`

处理规则：

1. `withdraw_address` 不能为空。
2. 建议最大长度 255。
3. 提现申请写入 `fa_miniapp_withdraw.withdraw_address`。
4. 后台提现记录列表展示该地址。

## 6. 注册接口新增提现密码

接口：

```text
POST /miniapp/user/do_register
```

新增参数：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| cash_password | string | 是 | 提现密码 |

原有参数不变：

- `tel`
- `pwd`
- `confirmPassword`
- `invite_code`
- `area_code`

处理规则：

1. `cash_password` 不能为空。
2. 建议长度不少于 6 位。
3. 注册成功后写入：

```php
'cash_password' => md5($cashPassword)
```

注意：

- 不修改原有登录密码字段。
- 不删除旧字段。
- 不新增其他小程序接口字段。

## 7. 后台充值提现审核方案

### 7.1 角色规则

| 操作人 | 处理方式 |
| --- | --- |
| 超管 | 直接完成，不需要审核 |
| 普通管理员/代理管理员 | 生成待审核记录 |
| 有上级管理员 | 由上级管理员审核 |
| 无上级管理员 | 由超管审核 |
| 管理员级别操作 | 由超管审核 |

### 7.2 充值流程

非超管提交充值：

1. 不立即增加用户余额。
2. 写入待审核记录。
3. 审核通过后增加余额。
4. 审核拒绝后不变动余额。

超管提交充值：

1. 直接增加余额。
2. 写入已完成充值流水。

### 7.3 提现流程

非超管提交提现：

1. 校验用户余额是否足够。
2. 不扣除余额，不增加冻结余额。
3. 写入待审核提现记录。
4. 审核通过时重新校验余额，余额足够后扣减余额，提现完成。
5. 审核拒绝后只更新状态，不变动余额。

超管提交提现：

1. 直接扣余额。
2. 写入已通过提现记录和资金流水。

### 8.2 后台充值提现审核表

```sql
CREATE TABLE `fa_miniapp_admin_balance_audit` (
  `id` int unsigned NOT NULL AUTO_INCREMENT,
  `user_id` int unsigned NOT NULL DEFAULT 0 COMMENT '小程序用户ID',
  `admin_id` int unsigned NOT NULL DEFAULT 0 COMMENT '发起管理员ID',
  `audit_admin_id` int unsigned NOT NULL DEFAULT 0 COMMENT '审核管理员ID,0表示超管',
  `type` tinyint unsigned NOT NULL DEFAULT 1 COMMENT '1充值 2提现',
  `amount` decimal(10,2) NOT NULL DEFAULT 0.00 COMMENT '金额',
  `order_no` varchar(64) NOT NULL DEFAULT '' COMMENT '单号',
  `withdraw_type` varchar(50) NOT NULL DEFAULT '' COMMENT '提现类型',
  `remark` varchar(255) NOT NULL DEFAULT '' COMMENT '备注',
  `status` tinyint NOT NULL DEFAULT 0 COMMENT '0待审 1通过 2拒绝',
  `audit_time` int unsigned NOT NULL DEFAULT 0 COMMENT '审核时间',
  `create_time` int unsigned NOT NULL DEFAULT 0,
  `update_time` int unsigned NOT NULL DEFAULT 0,
  PRIMARY KEY (`id`),
  KEY `idx_user_id` (`user_id`),
  KEY `idx_admin_id` (`admin_id`),
  KEY `idx_audit_admin_id` (`audit_admin_id`),
  KEY `idx_status_type` (`status`,`type`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='后台充值提现审核';
```

## 9. 验收用例

### 9.1 抢单商品轮询

前置条件：

- 有 3 个启用商品：A、B、C。
- 用户当天无未完成订单。

预期：

- 第 1 单商品 A。
- 第 2 单商品 B。
- 第 3 单商品 C。
- 第 4 单商品 A。

### 9.2 完成数量限制

前置条件：

- 系统任务数 `order_num = 60`。

预期：

- 当天完成 59 单时还能继续抢。
- 完成第 60 单后不能继续抢。
- 第二天按新的日期统计，完成数自然为 0。

### 9.3 提现地址

请求：

```text
POST /miniapp/ctrl/do_withdraw
num=100&type=USDT-TRC20&paypassword=123456&withdraw_address=Txxxx
```

预期：

- 提现申请成功。
- `fa_miniapp_withdraw.withdraw_address = Txxxx`。
- 后台提现记录展示 `Txxxx`。

### 9.4 注册提现密码

请求：

```text
POST /miniapp/user/do_register
tel=13800000000&pwd=123456&confirmPassword=123456&invite_code=ABCDEFGH&area_code=+86&cash_password=654321
```

预期：

- 注册成功。
- `fa_miniapp_user.cash_password = md5('654321')`。
- 后续提现使用 `654321` 校验通过。

### 9.5 后台充值提现审核

非超管充值：

- 提交后用户余额不变。
- 生成待审核记录。
- 上级或超管审核通过后余额增加。

非超管提现：

- 提交后用户余额不变，冻结余额不变。
- 审核通过后重新校验余额并扣除余额。
- 审核拒绝后只更新状态，不变动余额。

超管操作：

- 充值直接到账。
- 提现直接完成。

## 10. 风险点

1. 审核关系依赖现有管理员和小程序用户绑定关系，开发时需要复用当前 `admin_miniapp_user`、`parent_id`、管理员权限判断逻辑。
2. 提现审核必须使用事务和行锁，避免并发重复审核导致余额错误。
3. 抢单轮询必须保证 `orderInfo()` 和 `submit_order()` 商品一致，否则前端看到的商品和实际生成订单会不一致。
4. 不能把每日完成数写死为 60，应继续读取配置 `order_num`。
5. SQL 由人工执行，代码发布前必须确认字段和表已存在。
